## 2. 项目背景

FinOracle 面向银行监管政策、证券行业规范、保险制度等金融制度材料，最终需要完成文本、PDF 和图片文档解析、知识库构建、关键词检索、自然语言问答、条文关联查询与答案溯源。完整项目目标包括：知识库覆盖 1000 条以上核心知识点，系统响应时间不超过 2 秒，人工校验准确率不低于 85%。

当前仓库处于初建状态，仅具备 FastAPI 应用、`/api/v1/health` 健康检查接口及基础 pytest 测试，尚未接入 MySQL、Redis、用户认证和 RAG 能力。

本阶段以复习和实践后端工程知识为主要目的，先建设可复用的用户、认证、权限、缓存、测试及部署底座，为后续文档知识库和 RAG 问答模块提供稳定的用户身份与工程基础。

## 3. 阶段目标

### 3.1 产品目标

1. 建立普通用户和管理员两级账号体系。
2. 实现完整的用户注册、登录、令牌刷新、退出和强制下线流程。
3. 使用 JWT Access Token 与 Refresh Token 完成接口鉴权。
4. 使用 MySQL 持久化用户等结构化数据。
5. 使用 Redis 管理会话、令牌撤销、登录失败计数和后续通用缓存能力。
6. 使用 Docker Compose 提供一致、可复现的一键运行环境。
7. 建立统一异常、日志、配置、数据库迁移和自动化测试规范。
8. 为知识库管理、问答历史、收藏和制度文档权限预留用户关联能力。

### 3.2 学习目标

本阶段应覆盖 FastAPI 分层、RESTful API、Pydantic 数据校验、SQLAlchemy、Alembic、MySQL 索引与事务、Redis、JWT、密码安全、依赖注入、RBAC 基础、pytest、Postman 和 Docker Compose 等后端核心知识。

### 3.3 成功标准

- 新环境能够按照 README 使用 Docker Compose 一键启动 API、MySQL 和 Redis。
- 普通用户可完成注册、登录、访问个人信息、刷新令牌和退出登录的完整流程。
- 普通用户无法访问管理员接口或自行提升角色。
- 管理员可以查询、筛选、禁用和启用普通用户，并强制其全部下线。
- 令牌过期、退出、账号禁用和管理员强制下线后，受保护接口立即拒绝访问。
- 核心业务自动化测试覆盖率不低于 80%，验收用例全部通过。

## 4. 用户与角色

### 4.1 普通用户

普通用户通过公开注册接口创建账号，可登录系统、维护自己的基础资料，并在后续阶段使用知识问答、收藏和历史记录等功能。

### 4.2 管理员

管理员负责用户状态管理，并将在后续阶段负责制度文档和知识库管理。首个管理员由系统启动时根据环境变量初始化，公开注册接口不得创建管理员。

### 4.3 权限原则

- 本阶段采用 `user`、`admin` 两级角色模型。
- 普通用户只能访问本人资源。
- 管理员可以访问用户管理接口，但不能通过普通资料更新接口修改任何用户角色。
- 普通用户不能禁用、启用或强制下线其他用户。
- 管理员管理接口必须同时校验有效登录状态、账号状态和管理员角色。
- 首期不实现自定义角色、权限点配置和多租户。

## 5. 范围定义

### 5.1 本阶段范围

- 普通用户公开注册。
- 用户名或邮箱加密码登录。
- JWT Access Token 和 Refresh Token。
- Refresh Token 轮换、会话撤销和重复使用检测。
- 当前会话退出和全部会话退出。
- 当前用户信息查询与可编辑资料更新。
- 管理员用户列表、用户详情、状态管理和强制下线。
- Redis 会话、撤销状态、登录失败计数和限流基础能力。
- MySQL 数据持久化及 Alembic 迁移。
- 统一配置、错误响应、日志和请求追踪。
- 健康检查与就绪检查。
- Dockerfile、Docker Compose 和环境变量示例。
- pytest 自动化测试、覆盖率统计和 Postman Collection。
- README 使用说明。

### 5.2 本阶段不包含

- RAG 检索、LLM 问答和答案可信度评分。
- 文档上传、解析、OCR、切片和向量化。
- Milvus 或其他向量数据库。
- 前端页面。
- 邮箱验证、手机验证码、第三方登录和找回密码。
- 自定义角色、细粒度权限点和多租户。
- 用户头像文件上传。
- 问答历史、收藏和知识库管理的具体业务实现。

## 6. 总体方案

### 6.1 架构选择

本阶段采用模块化单体架构。FastAPI 应用按 API、业务服务、数据访问、安全与基础设施分层，各模块通过明确接口协作。该方案能够覆盖完整后端实践，同时避免当前规模下微服务带来的部署与通信复杂度。

### 6.2 逻辑分层

| 层级 | 职责 |
| --- | --- |
| API 层 | 路由、请求校验、认证依赖、响应组装 |
| Service 层 | 注册、登录、刷新、退出、用户管理等业务规则和事务边界 |
| Repository 层 | MySQL 数据访问，隔离 ORM 查询细节 |
| Security 层 | 密码哈希、JWT 签发与校验、权限判断 |
| Cache/Session 层 | Redis 会话、撤销状态、失败计数和缓存访问 |
| Core 层 | 配置、日志、异常、请求追踪和公共依赖 |

### 6.3 技术建议

- Python 3.11 或更高版本。
- FastAPI、Pydantic Settings。
- SQLAlchemy 2.x、Alembic、MySQL 8.x。
- Redis 7.x。
- JWT 库使用维护活跃且支持标准声明校验的 Python 实现。
- 密码哈希优先使用 Argon2id；如选择 bcrypt，需在实现文档中说明依赖和参数。
- pytest、pytest-cov、httpx。
- Docker、Docker Compose。

## 7. 核心业务流程

### 7.1 普通用户注册

1. 用户提交用户名、邮箱、密码和确认密码。
2. 系统规范化用户名和邮箱并完成格式、强度及一致性校验。
3. 系统检查用户名和邮箱是否已存在。
4. 系统对密码进行安全哈希后写入 MySQL。
5. 新用户角色固定为 `user`，账号状态默认为 `active`。
6. 系统返回已创建的非敏感用户信息，不自动授予管理员角色。

### 7.2 登录

1. 用户使用用户名或邮箱加密码登录。
2. 系统使用统一错误信息处理账号不存在和密码错误，避免泄露账号存在性。
3. 系统检查 Redis 登录失败计数和临时限制状态。
4. 密码正确后，系统检查账号是否启用。
5. 系统创建唯一会话 ID，并签发 Access Token 和 Refresh Token。
6. 系统将 Refresh Token 标识和会话状态写入 Redis，并更新最后登录时间。
7. 登录成功后清除该登录标识的失败计数。

### 7.3 访问受保护接口

1. 客户端通过 Bearer 方式提交 Access Token。
2. 系统校验签名、令牌类型、签发时间和过期时间。
3. 系统检查用户是否存在、账号是否启用、会话是否有效。
4. 管理员接口额外校验 `admin` 角色。
5. 校验通过后执行目标业务。

### 7.4 刷新令牌

1. 客户端提交未过期的 Refresh Token。
2. 系统校验令牌和 Redis 会话记录。
3. 系统废弃旧 Refresh Token 标识并签发新的双令牌。
4. 新 Refresh Token 继承同一登录会话，并在 Redis 中更新记录。
5. 旧 Refresh Token 再次使用时，系统判定为异常重放并撤销对应会话。

### 7.5 退出与强制下线

- 当前会话退出：撤销当前会话，使 Access Token 和 Refresh Token 均不能继续使用。
- 用户全部退出：撤销该用户的全部会话。
- 管理员强制下线：撤销目标用户全部会话。
- 禁用用户：更新 MySQL 账号状态，并立即撤销该用户全部会话。

## 8. 功能需求

### 8.1 注册

| 编号 | 需求 |
| --- | --- |
| AUTH-001 | 允许未登录访问者注册普通用户账号。 |
| AUTH-002 | 用户名和邮箱在系统内分别唯一。 |
| AUTH-003 | 邮箱比较前统一转换为小写。 |
| AUTH-004 | 用户名长度为 3–32 个字符，只允许字母、数字和下划线。 |
| AUTH-005 | 密码至少 8 个字符，并同时包含字母和数字。 |
| AUTH-006 | 注册请求必须包含与密码一致的确认密码。 |
| AUTH-007 | 请求中的角色、账号状态等敏感字段应被拒绝，不得静默接受。 |
| AUTH-008 | 密码不得以明文或可逆加密形式存储。 |

### 8.2 登录与会话

| 编号 | 需求 |
| --- | --- |
| AUTH-009 | 支持使用用户名或邮箱加密码登录。 |
| AUTH-010 | Access Token 有效期为 30 分钟。 |
| AUTH-011 | Refresh Token 有效期为 7 天。 |
| AUTH-012 | Access Token 与 Refresh Token 必须通过类型声明区分，不得混用。 |
| AUTH-013 | 每次刷新必须轮换 Refresh Token，旧令牌立即失效。 |
| AUTH-014 | 退出登录后，当前会话的所有令牌立即失效。 |
| AUTH-015 | 用户可以主动退出所有设备上的会话。 |
| AUTH-016 | 登录失败应累加 Redis 失败计数并触发短时限制，具体阈值默认采用连续 5 次失败后限制 15 分钟，并可通过配置调整。 |
| AUTH-017 | 登录成功后清除对应失败计数。 |

### 8.3 当前用户

| 编号 | 需求 |
| --- | --- |
| USER-001 | 登录用户可以查询自己的 ID、用户名、邮箱、角色、状态和时间信息。 |
| USER-002 | 登录用户可以更新允许编辑的基础资料。首期至少允许修改用户名和邮箱。 |
| USER-003 | 修改用户名或邮箱时继续执行格式和唯一性校验。 |
| USER-004 | 用户不能通过个人资料接口修改角色、状态、密码摘要或系统时间字段。 |
| USER-005 | 首期不提供密码修改与找回接口，避免在未设计再认证策略前引入不完整安全流程。 |

### 8.4 管理员

| 编号 | 需求 |
| --- | --- |
| ADMIN-001 | 系统首次启动时根据环境变量创建唯一初始化管理员；重复启动必须幂等。 |
| ADMIN-002 | 管理员可以分页查询用户列表。 |
| ADMIN-003 | 用户列表支持用户名或邮箱模糊搜索，以及角色、状态筛选。 |
| ADMIN-004 | 管理员可以查询指定用户详情。 |
| ADMIN-005 | 管理员可以禁用或启用普通用户。 |
| ADMIN-006 | 禁用用户时必须同步撤销其全部会话。 |
| ADMIN-007 | 管理员可以强制普通用户全部下线。 |
| ADMIN-008 | 普通用户不能访问任何管理员接口。 |
| ADMIN-009 | 首期接口不得修改管理员角色，也不得通过公开 API 禁用初始化管理员。 |

## 9. API 清单

统一前缀为 `/api/v1`。

| 方法 | 路径 | 访问权限 | 用途 |
| --- | --- | --- | --- |
| POST | `/auth/register` | 公开 | 注册普通用户 |
| POST | `/auth/login` | 公开 | 用户名或邮箱登录 |
| POST | `/auth/refresh` | 持有 Refresh Token | 轮换令牌 |
| POST | `/auth/logout` | 已登录 | 退出当前会话 |
| POST | `/auth/logout-all` | 已登录 | 退出全部会话 |
| GET | `/users/me` | 已登录 | 查询当前用户 |
| PATCH | `/users/me` | 已登录 | 更新当前用户资料 |
| GET | `/admin/users` | 管理员 | 分页查询用户 |
| GET | `/admin/users/{user_id}` | 管理员 | 查询用户详情 |
| PATCH | `/admin/users/{user_id}/status` | 管理员 | 启用或禁用用户 |
| POST | `/admin/users/{user_id}/logout-all` | 管理员 | 强制用户全部下线 |
| GET | `/health` | 公开 | API 存活检查 |
| GET | `/ready` | 公开 | MySQL、Redis 就绪检查 |

具体请求字段、响应字段、HTTP 状态码和业务错误码在实现计划或 API 契约中定义，但必须遵守本 PRD 的业务规则。

## 10. 数据设计

### 10.1 MySQL 用户表

建议 `users` 表至少包含以下字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 用户唯一标识，建议使用 UUID 或不可预测的唯一 ID |
| `username` | 唯一用户名 |
| `email` | 唯一邮箱，规范化后保存 |
| `password_hash` | 密码哈希 |
| `role` | `user` 或 `admin` |
| `status` | `active` 或 `disabled` |
| `last_login_at` | 最后登录时间，可为空 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

必须为规范化后的用户名和邮箱建立唯一索引。所有时间字段统一使用 UTC 保存，向客户端输出 ISO 8601 格式。

### 10.2 Redis 会话

每个登录会话至少记录：

- 会话 ID。
- 用户 ID。
- 当前 Refresh Token 的唯一标识或不可逆摘要。
- 创建时间和过期时间。
- 撤销状态。
- 可选的客户端信息，例如 User-Agent；不得将其作为唯一安全凭据。

Redis 还用于登录失败计数和短时限制。Redis 键名必须包含明确业务前缀和版本，避免未来模块冲突，并设置合理 TTL。

### 10.3 JWT 声明

JWT 至少包含：

- `sub`：用户 ID。
- `role`：签发时角色。
- `type`：`access` 或 `refresh`。
- `sid`：会话 ID。
- `jti`：令牌唯一标识。
- `iat`：签发时间。
- `exp`：过期时间。

服务端仍需验证用户与会话当前状态，不得仅依赖令牌中的角色和状态信息。

## 11. Redis 缓存边界

本阶段 Redis 的主要用途是认证会话、撤销状态、Refresh Token 轮换和登录失败限制。这些属于带过期时间的临时状态，不替代 MySQL 中的用户事实数据。

首期不缓存密码、密码摘要、完整用户敏感资料或管理员初始化凭据。应抽象独立的 Redis 访问组件，为后续制度条文热点数据和问答结果缓存预留能力，但本阶段不实现相关业务缓存。

## 12. 安全要求

1. JWT 密钥、数据库密码、Redis 凭据和初始化管理员密码只能从环境变量或安全配置注入。
2. 非开发环境检测到默认或弱 JWT 密钥时，应用必须拒绝启动。
3. 密码、完整 JWT、数据库密码和其他敏感信息不得写入日志。
4. 登录失败统一返回“账号或密码错误”。
5. 受保护接口必须检查令牌签名、类型、有效期、用户状态和会话状态。
6. 管理员接口必须进行服务端角色校验，不能依赖前端隐藏入口。
7. 所有输入使用 Pydantic 校验，数据库操作使用 ORM 参数绑定，防止注入。
8. OpenAPI 文档在生产环境是否开放应可配置。
9. 生产部署应由网关或反向代理提供 HTTPS；本阶段容器内部可使用 HTTP。
10. Refresh Token 不以明文持久化到 MySQL；Redis 中优先保存 `jti` 或不可逆摘要。

## 13. 错误处理与响应规范

错误响应应保持统一结构，至少包含：

```json
{
  "code": "AUTH_INVALID_CREDENTIALS",
  "message": "账号或密码错误",
  "request_id": "唯一请求追踪标识"
}
```

必须覆盖以下错误类型：

- 请求参数错误。
- 未认证或令牌格式错误。
- Access Token 或 Refresh Token 过期。
- 令牌类型错误、已撤销或检测到重复使用。
- 权限不足。
- 账号被禁用。
- 用户名或邮箱冲突。
- 资源不存在。
- 请求频率受限。
- MySQL 或 Redis 暂时不可用。
- 未预期服务端错误。

未知异常不得向客户端返回堆栈、SQL、密钥或内部文件路径。

## 14. 非功能需求

### 14.1 性能

- 在本地标准 Docker 环境、依赖服务正常且不计首次容器启动的条件下，认证与用户管理接口 P95 响应时间目标不超过 500 ms。
- 分页接口必须限制单页大小，默认 20，最大 100。
- Redis 操作必须设置超时，避免依赖故障长期阻塞请求。
- 当前阶段建立性能基线，为后续 RAG 问答整体不超过 2 秒的目标留出空间。

### 14.2 可用性与可观测性

- `/health` 只检查 API 进程存活，不依赖外部服务。
- `/ready` 检查 MySQL 和 Redis 连通性；任一关键依赖不可用时返回非就绪状态。
- 每个请求生成或透传 `request_id`，并写入结构化日志。
- 日志至少包含时间、级别、请求 ID、请求方法、路径、状态码和耗时。

### 14.3 可维护性

- 配置按环境注入，不在代码中硬编码。
- 数据库结构变更必须通过 Alembic 迁移，不依赖 ORM 自动建表作为正式方案。
- 路由层不得直接承载复杂业务规则或散落数据库查询。
- 新模块应能复用认证依赖、用户身份和统一错误响应。

## 15. Docker 与环境要求

### 15.1 服务组成

Docker Compose 至少包含：

- `api`：FastAPI 应用。
- `mysql`：MySQL 8.x，使用持久化卷。
- `redis`：Redis 7.x，使用持久化卷或明确配置允许的临时策略。

### 15.2 容器要求

- 各服务提供健康检查。
- API 在 MySQL 和 Redis 就绪后启动，并在服务前执行数据库迁移。
- 初始化管理员操作必须幂等。
- 提供 `.env.example`，列出变量名称和安全说明，不包含真实密钥。
- 开发配置支持代码热更新；生产镜像不包含测试缓存和无关开发文件。
- MySQL 和 Redis 数据使用具名卷，普通容器重建不得导致数据意外丢失。

### 15.3 建议环境变量

- 应用环境与日志级别。
- MySQL 主机、端口、数据库、用户和密码。
- Redis 主机、端口、数据库编号和可选密码。
- JWT 签名密钥、算法和令牌有效期。
- 初始化管理员用户名、邮箱和密码。
- OpenAPI 文档开关。
- 登录失败阈值与限制时长。

## 16. 测试要求

### 16.1 自动化测试

pytest 至少覆盖：

- 注册成功。
- 用户名重复、邮箱重复和参数不合法。
- 用户名登录、邮箱登录、密码错误和不存在账号。
- 登录失败计数和短时限制。
- Access Token 正常访问、过期、篡改和类型错误。
- Refresh Token 正常轮换、过期、撤销和重复使用。
- 当前会话退出和全部会话退出。
- 禁用用户无法登录、刷新或访问受保护接口。
- 普通用户访问管理员接口被拒绝。
- 管理员分页、筛选、禁用、启用和强制下线。
- 初始化管理员幂等。
- MySQL 或 Redis 不可用时的就绪检查和错误响应。

核心业务代码测试覆盖率不得低于 80%。测试数据与生产数据必须隔离。

### 16.2 Postman

交付 Postman Collection 和环境变量示例，至少包含以下串联场景：

1. 注册普通用户。
2. 登录并保存双令牌。
3. 使用 Access Token 查询当前用户。
4. 使用 Refresh Token 完成轮换。
5. 退出当前会话并验证旧令牌失效。
6. 管理员登录、查询用户、禁用用户。
7. 验证被禁用用户无法继续访问。

## 20. 已确认决策

- 采用模块化单体，而非极简脚本或微服务。
- 角色包括普通用户和管理员。
- 普通用户开放注册，管理员通过环境变量初始化。
- 支持用户名或邮箱加密码登录。
- 暂不加入手机号、验证码、第三方登录和邮箱验证。
- Access Token 有效期 30 分钟。
- Refresh Token 有效期 7 天并启用轮换。
- Redis 管理会话、撤销、重放检测和登录失败限制。
- 管理员可禁用用户并强制全部下线。
- Docker Compose 是本阶段正式交付内容。
